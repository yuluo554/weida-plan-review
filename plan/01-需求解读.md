# 01 需求解读

## 1. 赛题原文摘录（与本项目相关部分）

**赛题 1：工程大模型 Agent 智能应用系统设计**

> 本赛题要求参赛队伍结合 AI 大模型技术，针对工程建设行业的痛点需求，通过自主采集行业数据、选择技术路径与开发平台，完成 AI 大模型微调、领域知识库构建及智能体应用编排等任务。参赛团队可自由选择国内外大模型及开发框架，鼓励通过微调或插件开发提升模型在工程领域的专业表现。
>
> 参赛队伍需从以下两个核心主题中任选其一进行竞赛。

**主题 1：危大工程专项方案的智能审查**

> 场景痛点：危大工程（深基坑、高支模、起重吊装等）专项施工方案审查，存在方案体量大、人工审查效率低、依赖专家经验、易出现漏审错审、审查标准不统一等问题，难以适配工程建设的进度与合规要求。
>
> 竞赛要求：本主题聚焦于通过提取行业规范条款构建垂直领域知识库，利用大模型技术实现工程方案文本的自动化解析、合规性比对及关键参数校验等。鼓励集成方案缺陷自动标注、合规性智能判定与整改建议自动生成等核心功能，覆盖方案编制、审核、专家论证及技术交底等工程应用场景，进而深度赋能工程建设安全生命周期。

**初赛提交内容**：
1. 项目方案文件（Word/PDF，5000–8000 字）：技术路径、创新优势、应用场景等，建议突出与传统方案的差异与价值。
2. PPT 文件（PPT/PDF，16:9）：项目说明、创新点、技术路线、市场价值分析，绘制系统架构图，展示各模块逻辑关系。

> 注：初赛评审以文档为主，但一个可运行、可评测、可公开访问的系统是"技术路线真实可行"的最强证据，并直接支撑决赛。因此本项目按"真系统"标准建设，初赛材料从系统与评测结果中提炼。

## 2. 选题决策：为什么选主题 1

| 维度 | 主题 1：方案智能审查 | 主题 2：安全隐患识别 |
| --- | --- | --- |
| 输入模态 | 文本（docx/pdf），可全流程程序化 | 图像/视频为主，需多模态融合 |
| 算力要求 | CPU 即可 | 目标检测训练需 GPU |
| 数据获取 | 规范条款公开；方案可用生成器自制**带真值** | 需大量真实标注的隐患图像，自制困难 |
| 可解释性 | 结论逐条挂规范条款，天然可解释 | 检测框+分类，解释成本高 |
| 评测可重复 | 程序化生成配对数据，零 API 可重复评测 | 依赖图像数据集，扩充成本高 |
| 传统方案对比的"差异与价值" | 审查从"天"级到"秒"级，漏审可量化 | 巡检覆盖率提升，但业界 CV 方案已较成熟 |

**结论：选主题 1。** 若后续需切换主题 2，知识库、报告、评测与 Web 层可复用，仅解析层需替换为目标检测管线。

## 3. 用户与角色

| 角色 | 场景 | 系统给他的东西 |
| --- | --- | --- |
| 方案编制员（施工单位技术员） | 编完专项方案自检 | 漏项/超限清单 + 整改建议，改完即复审 |
| 审查工程师（总工/监理） | 收到方案要审 | 秒级预审报告，人工只看"待人工确认"项 |
| 论证专家 | 专家论证会 | 参数摘录 + 依据条款定位，快速抓住要点 |
| 安全监督员 | 合规留痕 | 带证据链的审查记录，可归档 |

| 赛题痛点 | 转译为系统能力 | 对应功能需求 |
| --- | --- | --- |

## 5. 功能需求清单（FR，带优先级）

优先级含义：P0 = 没有它不成为"审查系统"（MVP）；P1 = 初赛演示增强；P2 = 决赛加分。

### P0（MVP）

| 编号 | 需求 | 里程碑 |
| --- | --- | --- |
| FR-01 | docx 方案解析器：章节树 + 逐行文本 + 定位信息（章节/页/原文行） | M2 |
| FR-02 | 统一中间表示（参数卡）：实体-属性-值-单位-置信度-证据 | M2（骨架已定 Schema） |
| FR-03 | 规则库：深基坑样例规则 ≥20 条，JSON Schema 校验，版本化管理 | M3（骨架已给 5 条样例） |
| FR-04 | 规则引擎：threshold_min/max、required、enum、within_range；结论挂依据条款 | M3（骨架已实现前 3 类） |
| FR-05 | 审查报告：三级结论（合规/不合规/**待人工确认**）+ 证据 + 建议，先 Markdown 后 docx | M3/M5 |
| FR-06 | CLI 端到端：`planguard check 方案.docx --report output/` | M3 |

### P1（初赛演示增强）

| 编号 | 需求 | 里程碑 |

## 6. 非功能需求（NFR）

| 编号 | 需求 |
| --- | --- |
| NFR-01 | 可解释：每个结论必须带依据条款与原文证据，不允许"模型说违规" |
| NFR-02 | 可重复：基准评测零 API 依赖（纯规则通路），任何人 clone 后可复跑指标 |
| NFR-03 | 环境适配：Windows + Python 3.8 + Git Bash；核心链路（IR/规则引擎/CLI）零第三方依赖 |
| NFR-04 | 脱敏：样例数据全部程序化自制，不含真实项目名/人员/单位信息 |
| NFR-05 | 防幻觉：数值结论只出自确定性规则；LLM 输出必须"逐字摘录原文"且通过子串校验 |
| NFR-06 | 不硬判：多值冲突/低置信度一律输出"待人工确认"，不冒充确定结论 |

## 7. 边界与非目标（防 scope 失控）

**不做**：
- BIM/CAD 图纸几何审查
- 结构计算书复核（不重算稳定性/承载力，只校核方案文本参数与完备性）
- 扫描件 PDF 的 OCR（仅支持文本型 PDF）
- 移动端、多租户、云端部署（单机演示为限）
- 初赛阶段不做模型微调（用 API + RAG 覆盖"鼓励"项；决赛视评审反馈评估 LoRA/插件路线）

**不承诺**：
- 替代专家论证（工具定位：预审 + 辅助，最终结论人签）
- 法规时效性（阈值以官方现行文本为准，仓库内标注整理日期与"待核对"状态）

## 8. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 法规文本整理工作量大 | 先做深基坑一类打样（高频 20 条阈值），跑通后再横向扩类目 |
| 现场方案格式千奇百怪（文本框/表格/图片字） | 自制样例兜底回归 + LLM 兜底 + "待人工确认"级别兜住不确定 |
| LLM 服务不稳定 | 失败自动降级纯规则通路；评测不依赖 API |
| 赛程/截止日期未知 | 里程碑按周滚动（M1–M6），任何一周停止都有可用物 |
| 公开发布的合规风险 | 全部样例自制 + 脱敏四步审查（见 06 §3），赛题材料不入库 |
