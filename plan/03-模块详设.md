# 03 模块详设

## 1. 统一中间表示：参数卡（已实现，`planguard/ir/schema.py`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| param_id | str | 归一化参数标识，`<域>.<对象>.<属性>`，如 `dp.excavation_depth` |
| name | str | 中文参数名，如"基坑开挖深度" |
| value | float/None | 归一化数值（统一单位后） |
| unit | str | 计量单位，如 m / mm / kN / 次/d |
| raw_text | str | 原文数值表达（保留"≥5.4m"这类区间写法） |
| category | str | 工程类别：deep_pit / formwork_support / lifting |
| confidence | float | 规则解析=1.0；LLM 兜底<1.0 |
| source | str | rule / llm / manual |
| evidence | Evidence | doc / section / page / line_text / char_start / char_end |

**param_id 命名规范**：`dp.*`（深基坑）、`fs.*`（高支模支撑）、`lf.*`（起重吊装）。
**别名归一表**（M2）：`aliases.json` 维护 中文别名 → param_id，如「开挖深度/基坑深度/挖深」→ `dp.excavation_depth`。

**结论 Finding**：rule_id / rule_name / level(强制|建议) / severity(error|warning|info) / **result(pass|fail|manual)** / basis(依据条款) / advice(建议) / detail(机器可读说明) / evidence_line(原文)。
**ReviewResult**：doc + cards + findings + meta（规则库版本、耗时、跳过规则），summary() 输出三级计数。

## 2. 解析器（M2，`planguard/parsers/`）

**接口**（`base.py` 已定义）：

```python
class BaseParser(ABC):
    suffixes: tuple            # 如 (".docx",)
    def parse(self, path) -> ParseResult
# ParseResult = doc_name + sections[Section(title, level, page, path)] + lines[TextLine(text, page, section_path, char_span)]
```

**docx 解析要点**：遍历 body 的段落与表格；章节识别优先用标题样式（Heading 1–3），正则兜底（`^[一二三四五六七八九十]+、`、`^\d+(\.\d+)*\s`）；表格逐格抽取并记录行列号。
**pdf 解析要点**：pdfplumber 逐页 `extract_text` + `extract_words`（词坐标），按 y 坐标聚类成行；仅支持文本型 PDF。

**必须防的工程陷阱清单**（每个解析器配回归样例）：

1. PDF/CAD 导出文本的**字符间伪空格**（"5. 4 m"）→ 数值抽取前规范化去空格
2. 多行标注需按 y/x 邻近**聚类合并**再解析（表格跨行、批注换行）
3. 合并行内多构件按标签**切分段**（一行写多个参数）
4. CRLF 残留、全角/半角数字与单位混用（５ vs 5，Ｍ vs m）
5. 区间表达归一："≥5"、"不小于5"、"5~8"（取多值 → 触发 manual）
6. 中文路径、GBK 控制台编码
7. **数值合法性范围校验**：超物理范围即丢弃（如深度 5400m）——防解析器抽错

**数值抽取**：`(\d+(?:\.\d+)?)\s*(mm|m|cm|kN|kPa|MPa|次/d|次/天|%|t|℃)` + 前置量词识别（"不小于/不低于/≥"→ 下限语义）。

## 3. 规则库 JSON Schema（样例已入库，`planguard/rules/data/deep_pit.sample.json`）

```json
{
  "id": "R-DP-021",
  "name": "支护结构顶部水平位移控制值上限",
  "category": "deep_pit",
  "check_type": "threshold_max",
  "param": "dp.retaining.displacement",
  "op": "<=", "value": 30, "unit": "mm",
  "basis": "GB 50497-2019 监测报警值要求（示例阈值，以官方文本为准）",
  "level": "强制", "severity": "error",
  "advice": "位移控制值实测 {value}{unit}，超过示例上限 {limit}{unit}；请复核监测报警值取值并与设计文件核对。",
  "enabled": true, "stage": "M3",
  "note": "示例阈值，正式入库前逐条核对官方文本"
}
```

**check_type 枚举与启用计划**：

| check_type | 语义 | 启用 |
| --- | --- | --- |
| required | 参数必须可提取（缺 → 漏项） | ✅ M3（骨架已实现） |
| threshold_min / threshold_max | 数值下限/上限校核 | ✅ M3（骨架已实现） |
| enum | 取值在允许集合内（如支护形式） | M3 |
| within_range | 区间校核（下限≤x≤上限） | M3 |
| conditional_program | 条件触发程序性检查（如深度≥5m→须专家论证） | M4 |
| formula / cross_ref | 参数间关系（如锚杆长度与倾角换算） | M4 |
| checklist_section | 章节完备性检查（31号文九项内容齐套） | M4 |

**裁决规则**：
- 同一参数多值冲突 → `manual`（待人工确认），不取最严值硬判
- 同一参数命中多条规则 → 全部输出，按 severity 排序（error > warning > info）
- `level=强制` 违反 → 计入"不合规"；`level=建议` 违反 → 计入"建议项"；有疑问 → "待人工确认"

## 4. 知识库三层（M3/M4，`planguard/knowledge/`）

```
L1 原文层   data/knowledge/raw/      官方规范 PDF/docx（公开文本，登记来源）
L2 条文块层 data/knowledge/blocks/   {doc, chapter, article_no, text, tags} JSON —— 检索与引用单位
L3 阈值表层 data/knowledge/thresholds/ {param, op, value, unit, condition, basis} —— 机器可读，规则库的上游
```

- 检索：jieba 分词 + TF 余弦（数百条文规模，纯 Python 足够，不引 faiss）
- 问答路由：问题 → L3 结构化命中则直接回答（挂条款号）；未命中 → L2 检索 top-k → LLM 基于**逐字摘录**生成，摘录不是原文子串即丢弃
- 全部阈值标注「以官方文本为准」+ 整理日期

**来源清单（整理顺序，条文编号入库前逐条核对）**：住建部令第 37 号《危险性较大的分部分项工程安全管理规定》；建办质〔2018〕31 号（危大工程范围、专项方案九项内容、论证要求）；JGJ 120-2012 基坑支护；GB 50497-2019 基坑监测；JGJ 162-2008 模板安全；JGJ 130-2011 扣件式钢管脚手架；JGJ 311-2013 深基坑施工安全。

## 5. LLM 兜底与防幻觉（M4，`planguard/llm/`）

- **触发条件**：规则解析未命中的目标参数（候选行压缩后送审）
- **防幻觉三件套**：
  1. 候选行压缩：只送含数字/目标关键词的行，控制 token 成本
  2. 输出必须含"条款编号 + 逐字摘录"，摘录不是原文子串 → 整条丢弃
  3. 数值合法性范围校验，超范围丢弃
- **客户端约定**：OpenAI 兼容接口；`enable_thinking=false`（qwen 系大幅提速）；max_tokens 截断后的 JSON 修复；重试 + 超时；失败**降级到纯规则通路**
- **配置**：`.env`（LLM_BASE_URL / LLM_API_KEY / LLM_MODEL），`.env` 不入库，提供 `.env.example`

## 6. 编排器（M3，`planguard/orchestrator.py`）

轻量状态机：`load_doc → parse → extract_cards → load_rules → check → merge_verdicts → report`。
每节点记录耗时/输入输出计数；CLI `check` 与 Web 面板共用同一编排器；单节点失败给出可读错误与修复提示（缺文件/坏格式/依赖未装）。

## 7. 审查报告结构（M3 Markdown → M5 docx）

1. 封面：项目名 / 审查时间 / 规则库版本 / 工具版本
2. 总体结论：合规 X 项 · 不合规 Y 项 · 待人工确认 Z 项
3. 不合规清单（表）：规则 / 结论 / 依据条款 / 原文证据 / 整改建议
4. 待人工确认清单：冲突描述 + 两处原文
5. 通过项汇总
6. 附录：参数卡全表（含置信度与证据）
7. 签署栏：审查人 / 日期（报告不替代专家论证）

## 8. 测试策略

- 每个解析器配生成器样例做回归（输入 docx → 期望参数卡 JSON 断言）
- 规则引擎：每类 check_type 至少 1 正 1 反 1 边界（多值/缺参/超范围）
- 失败路径：缺文件 / 坏格式 docx / 依赖未安装 / LLM 不可达（应降级不崩溃）
- 命令：`py -m unittest discover -v`（零依赖）；M4 起加基准脚本冒烟
